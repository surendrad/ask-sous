# Phase 3: Agent Core (Insights Q&A) — Implementation Plan

**Date:** 2026-07-15
**Status:** In Progress
**Source:** implementation-plan.md Phase 3

---

## Goal

Turn Phase 2's four proven aggregation functions into an actual conversational agent: a Vertex AI (Gemini Flash 2.5) client that can call those functions — plus a new, carefully-guarded raw read-only SQL tool — as native function-calling tools, assemble their results into a grounded natural-language answer, log every step of that process for audit, and expose the whole thing through a `/chat` API endpoint that can be exercised end-to-end without any frontend. This is the phase where "grounded, never-invented numbers" (master-plan.md §9's core success metric) stops being a design intention for the data layer and becomes an actual, running conversation loop — and where the project's read-only DB boundary meets its highest-risk surface: a tool that executes SQL text that ultimately originates from model output.

Because live GCP credentials are not available in this implementation environment (`.env` still has placeholder values for `GOOGLE_APPLICATION_CREDENTIALS`/`GCP_PROJECT_ID` — `docs/reference/gcp-setup.md` has not been completed), this phase is deliberately split into two tracks throughout: everything buildable and testable *now* using fixtures/mocks at a well-defined SDK boundary, and the one thing — an actual live model call — that can only be verified once the user completes the GCP checklist. See Dependencies & Risks for how that gap is tracked.

## Prerequisites

- Phases 0–2 complete: FastAPI shell with `/health`, structlog JSON logging, `{data, error}` envelope helpers (`app/core/responses.py`), global exception handlers (`app/core/errors.py`), fail-fast `Settings`; full seeded schema; four working aggregation tools (`app/agent/tools/{revenue_summary,item_velocity,period_comparison,cohort_comparison}.py`) plus the read-only connection path (`app/agent/tools/db.py`).
- Local Postgres instance running, migrated, seeded (`cd backend && alembic upgrade head && python -m app.seed.seed`) — same generic "whatever `DATABASE_URL` points at" framing used by Phase 1/2's plans, since Docker is not installed in this implementation environment (carried forward, not new this phase).
- Backend virtualenv active, `pip install -e ".[dev]"` from `backend/`.
- **New runtime dependencies this phase**, to be added to `backend/pyproject.toml`'s `[project.dependencies]`:
  - `google-genai` — the Vertex AI SDK, per stack.md. Installable and importable without valid GCP credentials; only actual `.generate_content()` network calls require auth. This matters for the mocking strategy below — object construction (client, request/response types) is pure Python and fully testable offline.
  - `sqlglot` — SQL parser/AST library used to validate the raw SQL tool's queries are genuinely SELECT-only (see 3.1). A well-maintained, dependency-light, pure-Python library; no network/native-binary requirements, safe to add.
- **GCP/Vertex AI setup is NOT a prerequisite for building or testing this phase** — it is only a prerequisite for the subset of UAT scenarios explicitly marked "requires live credentials" below. Everything else (tool schemas, the tool-calling loop, the raw SQL guard, audit logging, the `/chat` endpoint, all automated tests) is buildable and verifiable against fixtures today.

## Implementation Details

### 3.1 Agent setup — Vertex AI client, tool schemas, raw SQL tool, response assembly

**Client adapter, not a raw SDK dependency scattered through the codebase.** `backend/app/agent/llm_client.py` wraps `google.genai.Client` behind a small `GeminiClient` class with one important design choice: the rest of the agent code never touches `google.genai` response types directly. `GeminiClient.generate_turn(contents, tools, model)` returns the app's *own* frozen dataclasses — `ToolCallRequest(name: str, args: dict, call_id: str)` and `FinalAnswer(text: str)` (a `LlmTurnResult = list[ToolCallRequest] | FinalAnswer` union) — translated from whatever the SDK's `GenerateContentResponse` actually contains. This is the concrete answer to "how do we test this without live GCP access": every layer *above* `GeminiClient` (the tool-calling loop, the `/chat` endpoint, audit logging) is tested by mocking `GeminiClient.generate_turn` itself with `AsyncMock`, returning hand-built instances of the app's own simple dataclasses — no need to fake the SDK's actual response shape anywhere except in the one place that translates it. `GeminiClient.__init__` constructs `genai.Client(vertexai=True, project=settings.gcp_project_id, location=settings.gcp_region)` — this construction alone requires no network call and no valid credentials, so it's testable directly (assert the client is configured with the right project/region from `Settings`) even with placeholder `.env` values.

**Confirm the exact Flash model identifier.** "Gemini Flash 2.5" (master-plan.md §4.4) is a product name, not an exact Vertex AI model ID (real IDs look like `gemini-2.5-flash`, and exact availability/naming can move). Record the confirmed model ID as a named constant, `FLASH_MODEL = "gemini-2.5-flash"` (or whatever `google-genai`'s current model catalogue confirms once the user has live access — flagged as an ADR, see Documentation Updates, since this is exactly the kind of "confirm current model availability at the start of Phase 3" risk the implementation plan's Risk Register already names). Pro-tier model selection is explicitly out of scope this phase (Phase 5's job, per implementation-plan.md) — `GeminiClient` accepts `model: str` as a parameter on every call rather than hardcoding Flash internally, so Phase 5 can pass a different model string without changing this module.

**Tool schemas — explicit JSON-schema declarations, not SDK auto-introspection.** `backend/app/agent/tool_registry.py` defines, for each of the four Phase 2 tools plus the new raw SQL tool, a `google.genai.types.FunctionDeclaration` built explicitly (not derived automatically from the Python function's type hints) — because none of the four tools' native Python types (`uuid.UUID`, `datetime.date`, `Decimal`) map cleanly onto JSON Schema on their own, and explicit declarations keep the exact contract the model sees fully visible, reviewable, and independently unit-testable (assert each declaration's `parameters.properties` has the expected keys/types), rather than depending on introspection behaviour from a package version that could change:

  - `get_revenue_summary`: `restaurant_id` (string, description notes UUID format), `start_date`/`end_date` (string, ISO `YYYY-MM-DD`, described as such — Gemini has no native date type).
  - `get_item_velocity`: `restaurant_id`, `window_start`/`window_end` (same string/ISO-date treatment), optional `menu_item_name` (string), optional `top_n` (integer).
  - `compare_periods`: `restaurant_id`, `period_start`/`period_end` (string/ISO-date).
  - `get_cohort_comparison`: `restaurant_id`, `start_date`/`end_date` (string/ISO-date), `metric` (string, `enum` populated from `list(cohort_comparison._METRIC_EXPRESSIONS.keys())` imported directly from Phase 2's module — not re-typed as a duplicate literal list, so the two can never silently drift apart).
  - `run_readonly_query` (new, this phase — see below): `query` (string, description explicitly instructs "a single read-only SELECT statement using named bind parameters, e.g. `:start_date`, never string-interpolated values"), `params` (object, free-form key/value bind parameters).

  A single `INSIGHTS_TOOLS: list[types.Tool]` (one `Tool(function_declarations=[...])` grouping all five) is what gets passed to `GeminiClient.generate_turn`.

  Alongside the schemas, a **dispatch table** — `TOOL_DISPATCH: dict[str, ToolSpec]` where `ToolSpec` bundles the async callable, an `parse_args(raw_args: dict) -> dict` function (converts the model's JSON args — plain strings/numbers — into the real Python types each tool function expects: `uuid.UUID(raw_args["restaurant_id"])`, `date.fromisoformat(raw_args["start_date"])`, etc.), and a `serialize_result` step (see below). Argument parsing failures (bad UUID, bad date, invalid `top_n`) raise `ValueError`/`ValidationError`, caught by the tool-calling loop (3.1 below) and turned into an error `function_response` fed back to the model, not a crash.

**Result serialization — JSON-safe, information-preserving.** Phase 2's tools return frozen dataclasses containing `Decimal`, `date`, and `uuid.UUID` fields — none of which are natively JSON-serializable, and naively coercing `Decimal` to `float` risks the exact kind of silent precision loss this project's grounding story exists to avoid. `backend/app/agent/tool_registry.py` (or a small `serialization.py` helper it imports) provides a pure, recursive `_to_jsonable(value: Any) -> Any`: dataclass instances → `dict` via `dataclasses.asdict` then recursed; `Decimal` → `str` (preserves exact value as text, since the model only ever needs to read and quote it back, never do arithmetic on it — the arithmetic already happened in Phase 2's pure functions); `date` → `.isoformat()`; `uuid.UUID` → `str`; `list`/`tuple` → recursed list; everything else passed through. This is what gets attached to the `function_response` part sent back to the model.

**The raw SQL tool — the highest-risk code in the project.** `backend/app/agent/tools/raw_sql.py`, following the same pure/impure split every other tool module in `app/agent/tools/` already uses (CLAUDE.md's documented convention this phase is explicitly asked to carry forward). Three layers of defence, all *before* any query text reaches Postgres — deliberately redundant with the DB-level read-only role (ADR-002), not a replacement for it, since defence-in-depth matters most exactly where LLM-generated text is involved:

  1. **Structural validation (`_validate_select_only(query: str) -> None`, pure, no DB):** parse `query` with `sqlglot.parse(query, dialect="postgres")`. Reject (raise `ValueError` with a message the model will see, so it can retry) unless: (a) parsing yields **exactly one** statement (blocks `SELECT 1; DROP TABLE x`-style stacking); (b) that statement's root node is `sqlglot.exp.Select` (blocks `INSERT`/`UPDATE`/`DELETE`/`DROP`/`ALTER`/`GRANT`/`TRUNCATE`/`CALL`/`COPY` outright, since none of those parse to a `Select` root); (c) the parsed tree has no `INTO` clause (blocks `SELECT ... INTO new_table`, which is a write disguised as a `SELECT`); (d) walking the full parsed tree with `expression.find(exp.Insert, exp.Update, exp.Delete, exp.Drop, exp.Alter, exp.Create, exp.Grant, exp.TruncateTable, exp.Command)` finds nothing anywhere in the tree, not just at the root — this is what protects against a write hidden inside a CTE (`WITH x AS (INSERT ... RETURNING *) SELECT * FROM x`) or other nested construct that could otherwise slip past a root-node-only check.
  2. **Row cap (`_enforce_row_cap(query: str, max_rows: int = 200) -> str`, pure):** wraps the *validated* query as `SELECT * FROM (<query>) AS _capped LIMIT :ask_sous_max_rows`, regardless of whether the original query already has its own `LIMIT`. Wrapping (rather than parsing/rewriting an existing `LIMIT` clause in place) is deliberately the simpler, more robust option — it can't be confused by a query that already has a differently-valued `LIMIT`, and it works uniformly whether or not one was present.
  3. **Statement timeout, applied in the same transaction as the query itself:** `run_readonly_query()` (the async wrapper) opens `readonly_connection()` (from `app/agent/tools/db.py` — this tool is bound by the exact same hard boundary as every Phase 2 tool, nothing new introduced here) and, before executing the caller's query, runs `SET LOCAL statement_timeout = '5000ms'` — a hardcoded constant, never built from caller input, so there's no injection surface in that statement itself. This bounds worst-case query cost (e.g. an accidental cross-join) independent of the row cap.

  ```python
  @dataclass(frozen=True)
  class QueryResult:
      columns: list[str]
      rows: list[dict[str, Any]]
      row_count: int
      truncated: bool  # True if row_count == max_rows (can't distinguish "exactly capped" from "more existed" without an extra COUNT — documented, not solved, this phase; see Dependencies & Risks)

  async def run_readonly_query(query: str, params: dict[str, Any] | None = None) -> QueryResult: ...
  ```

  `params` are passed to SQLAlchemy's `text(...).bindparams(...)` exactly as every Phase 2 tool already does for its own values — this tool's "parameterised" guarantee (master-plan.md §4.2, CLAUDE.md) rests on the model being instructed (via the tool's own JSON-schema description, and the system prompt) to always use named binds for *values*, while the *query shape itself* (which tables/columns, what `WHERE`/`GROUP BY` clauses) is the one thing genuinely LLM-authored text here — which is exactly why layer 1 exists: no amount of bind-parameterising the *values* protects against the *query itself* being a write, only structural validation of the parsed statement does that.

**Response assembly — the tool-calling loop.** `backend/app/agent/insights.py`'s `async def answer_question(restaurant_id: uuid.UUID, question: str) -> AgentTurnResult`:
  1. Build the initial `contents` (system instruction from `app/agent/prompts/insights_qa.py` — see below — plus the user's question, with `restaurant_id` injected into the system instruction so the model always has it without the user having to state it).
  2. Loop up to `MAX_TOOL_CALL_ROUNDS = 5` times: call `GeminiClient.generate_turn(contents, tools=INSIGHTS_TOOLS, model=FLASH_MODEL)`. If the result is `FinalAnswer`, break. If it's `list[ToolCallRequest]`, execute each via `TOOL_DISPATCH` (parse args → call → serialize result, or catch and serialize an error dict on failure — never letting one bad tool call abort the whole turn), log each call (3.2), append both the model's function-call turn and the tool results as a `function_response` turn to `contents`, and loop again.
  3. If `MAX_TOOL_CALL_ROUNDS` is exhausted without a `FinalAnswer`, raise a domain exception (`AgentIncompleteError`) rather than silently returning a partial/empty answer — this is a real, if rare, failure mode worth surfacing distinctly rather than papering over.
  4. Return `AgentTurnResult(answer: str, tool_calls: list[ToolCallRecord], model: str)` — the same structure that both feeds structured logging (3.2) and the `/chat` response body (3.3).

**System instruction** (`app/agent/prompts/insights_qa.py`, filling the previously-empty `prompts/` stub package): a constant `SYSTEM_INSTRUCTION_TEMPLATE` stating the agent's role, the current `restaurant_id` in scope, and — explicitly, in the model's own instructions, not just in this plan's prose — the grounding rule: *"Only state a number if it was returned by a tool call in this conversation. If the available tools can't answer the question, say so rather than guessing. Prefer the pre-built aggregation tools over `run_readonly_query` whenever one of them already answers the question."* This is necessary but insufficient by itself (a prompt is a request, not a guarantee) — see 3.2 for what's actually enforced/tested, not just asked for.

### 3.2 Grounding & audit logging

**Every agent turn is logged as one structured event per meaningful step**, via `structlog`, following the exact JSON-configured pattern from `app/core/logging.py` (Phase 0) — no new logging setup needed, only new call sites. `backend/app/agent/insights.py`'s `answer_question()` binds a per-turn correlation id via `structlog.contextvars.bind_contextvars(turn_id=str(uuid.uuid4()), restaurant_id=str(restaurant_id))` at the start (cleared in a `finally` block via `structlog.contextvars.clear_contextvars()`), so every log line emitted during that turn — including from deep inside a tool call — carries the same `turn_id` without having to thread it through every function signature by hand.

Concretely, these events are emitted (all via `logger.info(...)`, structured kwargs, not string interpolation):
- `agent_turn_started` — `question`, `restaurant_id`.
- `tool_call_requested` — `tool_name`, `arguments` (the parsed, real-typed args — post-`parse_args`, so a logged `restaurant_id` is loggable as its string form, not the raw model JSON), for every tool call, whether it succeeds or fails.
- `tool_call_result` — `tool_name`, `result` (the same `_to_jsonable()`-serialized form fed back to the model, so what's logged and what the model saw are provably the same object) **or** `error` (if the tool raised) — one event per tool call, always emitted, success or failure.
- `agent_turn_model_selected` — `model` (currently always `FLASH_MODEL` this phase — the field exists now so Phase 5's routing decision has somewhere to log *to* without a schema change).
- `agent_turn_completed` — `answer` (the final text), `tool_call_count`.

This satisfies CLAUDE.md's audit requirement literally: question, every tool call with arguments, each tool's raw result, which model handled the turn, and the final answer, all present as structured fields on logged events for every turn.

**"No naked numbers," enforced by construction as far as this phase's architecture allows, plus a best-effort automatic check, plus a test-level guard — three complementary layers, not one silver bullet:**
1. **By construction:** the model's final answer text is not permitted to be generated in a single unguided shot — `answer_question()`'s loop (3.1) only reaches a `FinalAnswer` after the model has had the opportunity to call tools and see their results injected back into `contents`; the system instruction (3.1) explicitly directs it to answer only from tool results. This is real, but it is a *request*, not a *guarantee* — the model could still, in principle, state a number from its own general knowledge rather than a tool result, and nothing in a function-calling architecture can fully prevent that without either (a) constrained decoding forcing every numeric token to be copy-pasted from a tool result (out of scope for this phase's tooling) or (b) full answer-vs-tool-result number cross-referencing (see below, and its documented limits).
2. **Best-effort automatic check, logged not blocking:** after assembling `AgentTurnResult`, a small pure function `_check_grounding(answer: str, tool_calls: list[ToolCallRecord]) -> bool` (regex `\d` scan of `answer`) — if the answer contains any digit characters and `tool_calls` is empty, log a `structlog.warning("possible_ungrounded_numeric_answer", ...)` event. This is deliberately a warning, not a blocking error: a legitimate answer can contain digits with no tool call behind them (e.g. "I can compare any two dates for you — for example, this week vs. last week" contains no data claim), so this is a signal for a developer reviewing logs, not an automated gate that would produce false-positive failures. This is the honest, testable version of "enforced by construction" this phase can actually ship — CLAUDE.md's rule remains, explicitly, also enforced in code review, not solely by this check.
3. **Test-level guard (the concrete deliverable implementation-plan.md's own Testing section names):** a guard test asserting that for a fixed set of test questions which *require* data to answer honestly (e.g. "what was my revenue last week?"), the mocked-`GeminiClient` fixture scenario used in the test always results in `tool_calls` being non-empty before a `FinalAnswer` is accepted — i.e. the test fixture itself is constructed so that if the mocked model tried to answer such a question with zero tool calls, the test would catch it, proving the loop's structure genuinely requires tool involvement for these scenarios rather than merely hoping for it.

### 3.3 Access point — `/chat` API endpoint

**Decision: build the FastAPI endpoint now, not a throwaway CLI script.** implementation-plan.md leaves this open ("whichever is faster to stand up first"). A CLI script would technically be marginally faster to type the first line of, but everything it would need — argument parsing, a response-formatting convention, error handling — already exists in this codebase for the API path and nowhere else: `app/core/responses.py`'s envelope helpers, `app/core/errors.py`'s exception-handler pattern, FastAPI's own request validation, and `httpx`/`TestClient`-based integration testing are all already established (Phase 0's `/health` endpoint and its smoke test are the direct precedent to extend). A CLI script would need to invent its own version of all of that, and — critically — Phase 6's plan already commits to a `/chat` endpoint as the thing the chat UI streams from, so building it now is strictly forward-work, not throwaway work, whereas a CLI script built today would likely be discarded once Phase 6 needs the real endpoint anyway. Non-streaming JSON is sufficient for this phase — Phase 6's own goal statement ("Streamed responses") is what introduces streaming, not Phase 3.

`backend/app/api/chat.py`:

```python
class ChatRequest(BaseModel):
    restaurant_id: uuid.UUID
    question: str = Field(min_length=1, max_length=2000)

class ToolCallSummary(BaseModel):
    tool_name: str
    arguments: dict
    result: dict | None
    error: str | None

class ChatResponseData(BaseModel):
    answer: str
    tool_calls: list[ToolCallSummary]
    model: str

@router.post("/chat")
async def chat(payload: ChatRequest) -> dict: ...
```

Handler flow: (1) confirm `restaurant_id` exists — a small `SELECT 1 FROM restaurants WHERE id = :restaurant_id` via `readonly_connection()` (reusing the exact same read-only path every tool uses, not a privileged connection just for this check); on no match, return the envelope's error shape with `code="restaurant_not_found"`, HTTP 404. (2) call `answer_question(restaurant_id, question)`. (3) wrap the returned `AgentTurnResult` into `ChatResponseData` and return `success(...)`. Including `tool_calls` in the response body (not just server-side logs) is deliberate — it's what lets the builder show "here's what it actually queried" directly from the API response during a demo, per master-plan.md §4.2's own framing, not only by tailing logs.

**Error handling — Vertex AI failures never silently swallowed, never retried indefinitely.** A new domain exception, `backend/app/agent/exceptions.py`: `AgentUnavailableError(Exception)` and `AgentIncompleteError(Exception)` (from 3.1). `GeminiClient.generate_turn()` catches `google.genai.errors.APIError` and any `google.api_core.exceptions.GoogleAPICallError` subclasses (rate limits, service unavailable, auth failures) and re-raises as `AgentUnavailableError` with the original exception chained (`raise AgentUnavailableError(...) from exc`) — the original is logged via `structlog.error(..., exc_info=exc)` before translation, so the full detail is captured server-side even though only a generic message reaches the client, matching the existing `unhandled_exception_handler` pattern in `app/core/errors.py`. **Zero automatic retries** — the simplest choice that trivially satisfies CLAUDE.md's "never retried indefinitely," and appropriate at this project's scale (a demo, not a production service with SLA pressure); if a Vertex AI call fails, the turn fails clearly and the user can just ask again. New handlers registered in `app/core/errors.py`, following the existing pattern exactly: `agent_unavailable_exception_handler` → HTTP 503, `error_response("The agent is temporarily unavailable. Please try again.", "agent_unavailable")`; `agent_incomplete_exception_handler` → HTTP 502 (the agent ran but couldn't converge on an answer within the tool-call round cap — a distinct, real failure mode, not "unavailable"), `error_response("The agent couldn't complete this request. Try rephrasing your question.", "agent_incomplete")`. Both registered on `app` in `main.py` via `app.add_exception_handler(...)`, alongside the existing two handlers.

## Security Considerations

- **The raw SQL tool (`run_readonly_query`) is the single highest-risk piece of code added this phase.** Even though the underlying DB connection is already restricted to a read-only role (defence layer already in place since Phase 0/2 — ADR-002), this phase adds a second, independent layer specifically because the *query text itself* originates, at least in part, from LLM output: structural SELECT-only validation via `sqlglot` (rejecting write statements anywhere in the parsed tree, not just at the root, closing the CTE-hides-a-write gap), a hard row cap applied via query wrapping, and a statement timeout. None of these three layers depends on the others — losing any one still leaves two — which is the intended defence-in-depth posture for the one place in this codebase where "LLM-generated text becomes a SQL injection vector even with parameterisation" (as this plan's brief itself names the risk) is a genuine, non-theoretical concern.
- **Restaurant-scoping is intentionally *not* hard-enforced inside `run_readonly_query`'s SQL itself.** Master-plan.md §5's permission model scopes the *chat UI experience* to the selected restaurant, but explicitly carves out cohort/peer comparisons as an intentional, non-leaking aggregation feature — and the raw SQL tool exists precisely to answer questions the pre-built tools (some of which are deliberately cross-restaurant, like `get_cohort_comparison`) can't. Hard-restricting every raw SQL query to a single `restaurant_id` would break that legitimate use case. This is a deliberate scope decision, documented here rather than left as an implicit gap: the read-only role plus the three query-safety layers above are the boundary; restaurant-level data scoping is a UI/product concern (there being no user accounts to violate — master-plan.md §2), not a SQL-level access-control concern in this project.
- **Vertex AI credentials remain out of the repo** — no change to the existing `.env`/`.gitignore` convention from Phase 0; this phase only *consumes* `GOOGLE_APPLICATION_CREDENTIALS`/`GCP_PROJECT_ID`/`GCP_REGION`, it doesn't introduce new secret-handling surface.
- **Error responses never leak internals** — `AgentUnavailableError`/`AgentIncompleteError` handlers return only generic messages; the original Vertex AI exception (which could otherwise include request/response internals) is logged server-side only, following the exact pattern `unhandled_exception_handler` already established.
- **New dependencies:** `google-genai` (official Google SDK, actively maintained, expected) and `sqlglot` (widely-used, pure-Python, no native extensions, active maintenance) — both reasonable additions per CLAUDE.md's "prefer well-maintained, actively-released dependencies" guidance. Run `pip audit` after adding them, per CLAUDE.md's periodic-audit convention.
- No authentication/authorisation changes — still no user accounts (master-plan.md §2). The new `/chat` endpoint has no auth, consistent with every other route in this project.

## Dependencies & Risks

- **Live Vertex AI calls cannot be tested in this implementation environment right now — first-class risk, not a footnote.** `.env` still has placeholder values for `GOOGLE_APPLICATION_CREDENTIALS`/`GCP_PROJECT_ID`; `docs/reference/gcp-setup.md`'s checklist has not been run. Everything in this plan except an actual network call to Vertex AI is buildable and testable today via the `GeminiClient` adapter/fixture strategy (3.1). The one thing that genuinely cannot be verified until the user completes that checklist is: does a *real* Gemini Flash 2.5 call, with the *real* tool schemas this phase defines, actually produce sensible function calls and a sensible final answer? UAT-3.5/3.6 are explicitly scoped to that gap and cannot be marked complete until then. This should be treated as an open item to revisit, not silently assumed to work because the mocked tests pass — mocked tests prove the *plumbing* is correct, not that the *real model* behaves as expected against these exact schemas.
- **Exact current Gemini model IDs may have moved since this plan was written**, per implementation-plan.md's own Risk Register entry for this phase ("Reference Gemini Pro-tier model has been deprecated/renamed since interview prep"). This phase only needs to confirm the Flash-tier ID; confirm it against the `google-genai` SDK's current model listing once live credentials exist, before UAT-3.5 is attempted, and record the confirmed ID in ADR-007 (Documentation Updates) rather than assuming the constant proposed in 3.1 is still correct at build time.
- **`sqlglot`'s SELECT-only validation is a static-analysis defence, not a formal proof.** It's a strong, well-tested layer (this plan's own unit tests exercise the CTE-hides-a-write case explicitly), but SQL is a large surface area and a sufficiently obscure Postgres-specific construct could theoretically slip past a general-purpose parser's write-detection in a way this phase's test suite doesn't anticipate. The DB-level read-only role (ADR-002) is what makes this an acceptable risk rather than a blocking one: even in the worst case where a write statement somehow parsed as if it weren't one, the `ask_sous_readonly` role itself would still reject the write at the database level. This two-layer relationship (structural validation to keep obviously-bad queries from even reaching Postgres, DB role as the actual last line of defence) should be stated plainly in ADR-006 rather than implying either layer alone is sufficient.
- **`QueryResult.truncated` is an approximation, not exact, per 3.1's own design note** — the row-cap wrapping approach can't cheaply distinguish "exactly `max_rows` rows existed" from "more existed and were cut off" without an extra `COUNT(*)` query (which would double query cost for every raw-SQL call). `truncated=True` whenever `row_count == max_rows` is a reasonable, honest-enough signal for a demo-scale project (the model can be told "there may be more results" rather than a definitive count) — flagged here so it isn't mistaken for a precise guarantee later.
- **No git repository initialized yet in this session** (carried forward from Phase 0/1/2, unchanged this phase) — `.gitignore`/`.pre-commit-config.yaml` are in place and ready; commit history still doesn't exist. Not blocking for this phase's implementation work, only for `pre-commit run --all-files` and version-controlled history.
- **Docker is not installed in this implementation environment** (carried forward, unchanged) — this phase's "run this against the database" tasks are written generically and apply to whichever local Postgres instance `DATABASE_URL` points at, per the same framing Phase 1/2 already established.
