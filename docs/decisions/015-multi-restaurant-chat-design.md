# ADR-015: Multi-Restaurant Chat Design

**Date:** 2026-07-16
**Status:** Accepted

## Context

The user's Phase 8 request (item 1) was explicit: "provide an ability to select all the locations from the drop down so the dashboard shows data across the selected locations and Chat can answer questions as well." Every prior phase's `/chat` and insights orchestration (`app/agent/insights.py`, `app/api/chat.py`) was built around exactly one `restaurant_id: uuid.UUID` — there was no existing concept of "the currently selected set of restaurants" anywhere in the backend. This had to be introduced without breaking the grounding/audit-logging guarantees every prior phase's tests already lock in (per-turn structured logging, "no naked numbers," the read-only DB boundary).

## Decision

**`restaurant_id: uuid.UUID` becomes `restaurant_ids: list[uuid.UUID]` everywhere in the insights/chat pipeline — a list of one is the single-restaurant case, not a separate code path.** This mirrors the exact shape ADR-011 already established for a different concern: rather than adding an `is_multi: bool` flag or two parallel functions, `answer_question()`, `answer_question_stream()`, `build_insights_system_instruction()`, and `ChatRequest` all take the list unconditionally. `ChatRequest.restaurant_ids: list[uuid.UUID] = Field(min_length=1)` enforces "at least one" at the API boundary via Pydantic rather than a runtime check.

**Two brand-new tools (`compare_locations`, `get_upsell_metrics`) are written list-first from the start**, each accepting `restaurant_ids: list[uuid.UUID]` and fanning out to per-restaurant queries via `asyncio.gather` — "a single-location call is just a list of one" is the literal reasoning recorded in `upsell_metrics.py`'s own docstring. Both reuse an existing single-restaurant tool internally (`compare_locations` calls `get_revenue_summary` per id) or a new but still per-restaurant SQL query, rather than writing a bespoke multi-restaurant SQL query with `WHERE restaurant_id = ANY(...)` — this keeps per-restaurant business logic in one place and reuses the existing tool's own tests as a correctness baseline.

**The system instruction gets an explicit selection-count branch, not a single unified paragraph.** `build_insights_system_instruction()` switches between `_SINGLE_RESTAURANT_GUIDANCE` (use the existing single-restaurant tools directly) and `_MULTI_RESTAURANT_GUIDANCE` (use `compare_locations`/`get_upsell_metrics` with the full list; explicitly do **not** call a single-restaurant tool once per restaurant to fake a comparison) when more than one restaurant is selected. This was a deliberate, pragmatic choice over generalizing every existing insights tool (`get_revenue_summary`, `get_item_velocity`, `compare_periods`, `get_cohort_comparison`) to accept a list — that would be the architecturally cleaner end state (see the "why not generalize every tool" note below), but is materially larger scope than this phase's three specific asks required, and every one of those tools already has its own established single-restaurant test suite and call sites from Phases 2–3 that a blanket signature change would ripple through.

**`GET /dashboard` follows the identical pattern**: `restaurant_ids: Annotated[list[uuid.UUID], Query()]` (repeated query params, not a comma-joined string, matching how FastAPI/Pydantic natively parse array query params) replaces the old singular `restaurant_id`, and the response becomes `{"locations": [...], "totals": {...}, "top_items": [...] | null}` — always an array of locations, so the frontend has exactly one shape to handle regardless of selection count, with `top_items` populated only when exactly one location is selected (see Consequences).

**`POST /campaigns` deliberately does *not* follow this pattern and stays single-restaurant.** Campaign copy generation reads one restaurant's `brand_voice_guide` and produces one piece of marketing copy in that restaurant's voice — there is no coherent single output for "campaign copy across 3 different restaurants with 3 different voices" the way there is a coherent single output for "combined revenue across 3 restaurants." The frontend enforces this: `CampaignsPanel` always scopes to `selectedRestaurantIds[0]` and disables its Generate action (with an explanatory `StatusTag`) whenever more than one restaurant is selected, rather than the backend silently picking one on the caller's behalf.

## Consequences

- **Breaking API change**, the second one `/chat` has had (ADR-011 broke it once already for SSE). `{"restaurant_id": "..."}` is no longer valid; every caller — the frontend, any manual `curl` testing, any future integration — must send `{"restaurant_ids": ["..."]}`. Documented in `CLAUDE.md` and this ADR so it doesn't read as an accidental regression to a future reader. `GET /dashboard?restaurant_id=...` similarly becomes `?restaurant_ids=...` (repeatable).
- **Tool-surface asymmetry, acknowledged rather than hidden.** `compare_locations`/`get_upsell_metrics` are list-first; `get_revenue_summary`, `get_item_velocity`, `compare_periods`, `get_cohort_comparison`, and the new `list_campaigns`/`get_campaign_performance` all remain single-restaurant/single-campaign. This is why the system instruction needs an explicit "don't fake a comparison by calling single-restaurant tools in a loop" warning, and why `GET /dashboard`'s `top_items` field is only populated for a single-location selection (`get_item_velocity` has no multi-restaurant form to call instead). The clean generalization — every insights tool takes `restaurant_ids: list[uuid.UUID]` uniformly, collapsing both the prompt's selection-count branch and the dashboard's `top_items` special case — is real future work, not done here because it's a strictly larger change than any of the three capabilities the user actually asked for in this phase.
- The read-only DB boundary and audit-logging guarantees are unaffected: every new tool still goes through `readonly_connection()` exclusively, and `answer_question()`/`answer_question_stream()`'s `structlog.contextvars.bind_contextvars()` call now binds `restaurant_ids` (a list) instead of `restaurant_id` (a scalar) — a field rename that ripples through log consumers/tests but changes no logging *behavior*.
- **A real bug, found only via a live `/chat` call, not the mocked test suite:** `compare_locations()`/`get_upsell_metrics()` are the first tools whose result serializes to a *list* rather than a single dict — `chat.py`'s `ToolCallSummary.result` was typed `dict | None`, which crashed building the terminal SSE `done` frame the moment a real multi-location comparison question actually produced a list-shaped tool result. No mocked test had ever exercised a list-shaped result, since every tool through Phase 7 returned exactly one dict. Fixed by widening the type to `dict | list | None` (mirrored in the frontend's `ChatToolCall.result`), with a regression test locking in the list case. Documented here as a concrete instance of why this project's "verify against live credentials, not just mocks" discipline (ADR-013) matters — a type that's "obviously" correct against every existing test can still be wrong the moment a new tool shape is introduced.
- Model routing (`_select_model()`, ADR-010) is unaffected by selection count — it still routes purely on tool-call-round count and "deeper analysis" keyword matching, regardless of how many restaurants are in scope for the turn.

## Alternatives Considered

- **Generalize every insights tool to accept `restaurant_ids: list[uuid.UUID]` up front, in this same phase.** This is the architecturally cleaner end state (see Consequences) and was raised as a `/simplify` altitude-review finding during this phase's own review pass. Rejected for now as materially larger scope than the user's three specific asks, and as unnecessary risk to Phase 2/3's already-tested single-restaurant call sites for a benefit (removing one prompt branch and one dashboard special case) that doesn't change any user-visible behavior today. Left as a documented "if this project grows, do this next" note rather than silently deferred.
- **A separate `compare_restaurants` endpoint/tool namespace, entirely distinct from the single-restaurant tools**, rather than reusing `restaurant_ids` as the parameter name pattern everywhere. Rejected: it would create two vocabularies for "which restaurant(s) is this about" instead of one, and the model would have to learn an entirely separate mental model for the multi-location case instead of "the same tools, just sometimes with a list of one."
- **Let `/campaigns` accept `restaurant_ids` too and silently generate for the first one, or concatenate multiple restaurants' copy into one response.** Rejected: silently picking a restaurant on the caller's behalf hides a real ambiguity from the user, and concatenating unrelated brand voices into one piece of marketing copy isn't a coherent product outcome — surfacing the constraint explicitly in the UI (disable + explain) is more honest than working around it in the API.
