# ADR-013: Live Credentials Verification — Two Real Bugs Found and Fixed

**Date:** 2026-07-16
**Status:** Accepted

## Context

Every phase from 3 onward carried an explicit, repeated caveat: the entire agent stack (Gemini function-calling, streaming, embeddings) was built and tested exclusively against mocked/fixture `google-genai` responses, since no live GCP credentials existed in the implementation environment. `docs/reference/gcp-setup.md` was the one manual, user-owned step that could never be automated. This ADR records what happened the first time real credentials were wired up and real calls were made — two genuine, previously-undiscovered bugs surfaced immediately, neither of which any mocked test could have caught, because both are about the *shape of what's actually sent to/read from the real SDK*, not about this app's own internal logic.

## What Was Found

**Bug 1 — `GOOGLE_APPLICATION_CREDENTIALS` was parsed into the app's `Settings` object but never exported to the OS environment.** `google.auth.default()` (the Application Default Credentials mechanism both `GeminiClient` and `EmbeddingClient` rely on) reads `os.environ["GOOGLE_APPLICATION_CREDENTIALS"]` directly — it has no knowledge of this app's own `pydantic-settings`-based config. Every real call failed with `DefaultCredentialsError`, identical to the "missing credentials" case both adapters already handled — so the failure was silent and indistinguishable from "just haven't set up GCP yet," until deliberately investigated. **Fixed** by adding `Settings.model_post_init()` to export the value as a real side effect of constructing any `Settings` instance. See `backend/app/core/config.py` and `backend/tests/unit/test_config.py`.

**Bug 2 — `types.Tool(function_declarations=[])` (an empty-but-present Tool object) is rejected by the real Vertex AI API** with `400 INVALID_ARGUMENT: tools[0].tool_type: required one_of 'tool_type' must have one initialized field`. `GeminiClient.generate_turn()`/`generate_turn_stream()` always wrapped the caller's `tools` list in a `types.Tool(...)`, even when that list was empty — and `campaigns.py`'s `generate_campaign()` *always* calls with `tools=[]` (deliberately, per ADR-011/the campaign generation design — no tools are offered, only a system-instruction-grounded single-shot generation). This meant **every real campaign generation call was broken**, 100% of the time, despite 100% of `campaigns.py`'s own tests passing — because the tests mock the SDK call boundary and never validate the constructed `config` object against the real API's actual validation rules. **Fixed** with a shared `_build_config()` helper that omits the `tools` field entirely from `GenerateContentConfig` when the tools list is empty, rather than sending an empty-but-present `Tool`. See `backend/app/agent/llm_client.py` and the new `test_generate_turn_omits_tools_from_config_when_none_given()`/`test_generate_turn_stream_omits_tools_from_config_when_none_given()` tests.

**A third finding, not a bug — a real UX gap surfaced by an actual model conversation.** Asking a live insights question with a relative date phrase ("last 7 days") caused the model to hallucinate calling nonexistent `today()`/`timedelta()` tools, then correctly decline to guess a date range rather than answer with an invented number — a real demonstration of the grounding discipline working as intended, but revealing that the system instruction never told the model what "today" actually is. **Fixed** by adding the current date to `build_insights_system_instruction()` (a new `today` parameter, defaulting to `date.today()`, injectable for tests). See `backend/app/agent/prompts/insights_system_instruction.py`.

## Consequences

- **This is the single clearest demonstration in the whole project of why "mocked tests prove the plumbing is correct, not that the real model/API behaves as expected" (a line repeated verbatim across ADR-007, ADR-008, and every phase's changelog entry) was not just defensive hedging.** Both bugs were 100%-reproducible, would have affected every real user of the deployed app, and were invisible to a fully-passing, fully-green test suite for the entire duration of Phases 3–7.
- Both fixes are small, targeted, and don't change any tested behavior for the mocked-call paths that already existed — `generate_turn`/`generate_turn_stream`'s existing tests (which always pass `tools=[]` or a populated list) still pass unchanged, since mocks never validated the *shape* of the config object, only that a config was passed.
- Verified end-to-end against the real, live Vertex AI project (`your-gcp-project-id`, region `us-central1`) after both fixes: a real insights Q&A turn with correct date resolution and a real grounded numeric answer; real token-by-token streaming; real function-calling with a populated tool; real campaign generation on `gemini-2.5-pro` with real few-shot retrieval (after running `embed_seed_data.py` for real — 138 reviews + 16 campaigns embedded via the real `text-embedding-004` model, confirmed 768-dimensional vectors). Model IDs (`gemini-2.5-flash`, `gemini-2.5-pro`, `text-embedding-004`) are now confirmed correct against the live API — the "not yet verified against a live listing" caveat in ADR-007/ADR-008/ADR-010 is resolved.
- **A genuine, separate content-quality limitation was also observed, not fixed here:** seeded review text (Phase 1's `generators.py`) uses generic Faker sentence generation, not restaurant-domain-realistic content, so real semantic vector search over reviews returns technically-correct nearest neighbors that are never actually *about* anything (service, food, etc.) — the model correctly and honestly reports finding nothing relevant, rather than hallucinating, which is the grounding rule working exactly as designed. This is a seed-data realism gap worth revisiting if qualitative-search demo quality matters, tracked here rather than silently noticed and dropped.

## Alternatives Considered

- **Setting `GOOGLE_APPLICATION_CREDENTIALS` inside each adapter's `__init__`** (`GeminiClient`, `EmbeddingClient`) instead of centrally in `Settings`. Rejected: both adapters already read `Settings` at construction time, and any other future code path that might need ADC (a script, a different SDK call) would otherwise need to remember to do this itself. Exporting once, as a side effect of `Settings` construction, is the single point of truth.
- **Sending `tools=None` explicitly instead of omitting the config field.** Equivalent in practice (`GenerateContentConfig(tools=None, ...)` and `GenerateContentConfig(...)` without `tools` produce the same unset field) — the implementation uses the "don't pass the field at all" form since it's what `_build_config()`'s early-return branch naturally produces.
