# ADR-011: SSE Streaming for `/chat` and Mid-Stream Error Handling

**Date:** 2026-07-16
**Status:** Accepted

## Context

`stack.md` and implementation-plan.md 6.1 both call for genuine token-by-token streaming on `/chat` ("Streamed responses (token-by-token)... rendered as they arrive"), not a client-side simulation over a single JSON response — confirmed explicitly with the user before this phase's plan was written (`docs/plans/phase-6-frontend.md`'s Goal section records that decision). The Risk Register in implementation-plan.md already anticipated the corresponding audit-logging complication: "log the full assembled response server-side after the stream completes, not just what's sent to the client." This phase had to make that concrete: how the SDK's streaming call bridges into the app's existing async orchestration, how the wire format looks, and how a failure that happens *after* streaming has already started differs from one that happens before.

## Decision

**Wire format: Server-Sent Events (`text/event-stream`), not WebSockets.** `/chat` is a one-shot request/response shape extended into a stream — the client sends one question and receives one stream back, never sends further messages on the same connection. SSE is the right-sized tool for that; WebSockets would add bidirectional-connection machinery this endpoint never uses. Each event is a JSON-encoded `data: {...}\n\n` frame with an explicit `type` discriminator: `text_chunk` (one piece of streamed answer text), `done` (the terminal event — same shape `ChatResponseData` already returned pre-streaming: `answer`, `tool_calls`, `model`), or `error` (see below).

**Bridging the SDK's synchronous stream.** `google-genai`'s `generate_content_stream()` returns a plain synchronous `Iterator[GenerateContentResponse]`, not an async iterator — there is no async-native streaming call on the installed SDK version. `GeminiClient.generate_turn_stream()` (`backend/app/agent/llm_client.py`) bridges this with a small generic helper, `_iter_in_thread()`: a background thread drains the sync iterator into an `asyncio.Queue`, and an async generator awaits and yields from that queue, re-raising any exception the thread surfaces. This is a new concurrency pattern for the codebase (everywhere else uses `asyncio.to_thread()` for a single blocking call, not a blocking *iterator*) — worth calling out explicitly rather than leaving it as an unremarked one-off.

**Orchestration: `answer_question_stream()` alongside, not replacing, `answer_question()`.** `backend/app/agent/insights.py` keeps both: `answer_question()` (unchanged, still used nowhere in this phase's `/chat` path but kept as the simplest non-streaming entry point for any future non-UI caller) and `answer_question_stream()`, which shares the same model-routing and round-cap logic and now shares the same per-round tool-dispatch-and-logging code via an extracted `_resolve_tool_call_round()` helper (this duplication was real once both existed, so it was factored out rather than left as two parallel copies — see the phase plan's own note anticipating this). `answer_question_stream()` yields `TextChunk` events as a final-answer round's text arrives, and a terminal `AgentTurnComplete` carrying the exact same `AgentTurnResult` `answer_question()` would have returned — this is the concrete mechanism for "log the full assembled response after the stream completes": the API layer logs/serves from that one terminal object, not from anything it patched together itself out of individual chunks.

**Mid-stream vs. pre-stream failures are handled differently, and this is an inherent SSE constraint, not a design choice.** Once the HTTP response has started (status 200, `text/event-stream` headers sent), there is no way to retroactively change it to a 503/502 — the client has already committed to reading a stream. So `POST /chat` pulls the *first* event from `answer_question_stream()` before constructing the `StreamingResponse` at all: if `AgentUnavailableError`/`AgentIncompleteError` is raised at that point (nothing sent yet), it propagates normally and hits the same global exception handlers every other endpoint uses (503/502 JSON, unchanged). Only a failure that happens *after* the first event has already been produced — mid-stream — is caught inside the `StreamingResponse`'s own generator and turned into a final `{"type": "error", ...}` SSE frame instead, using the same message/code the JSON handlers would have used, so the two failure modes are indistinguishable in content even though their transport differs. `_event_stream()`'s mid-stream handling also catches a bare `Exception`, not just the two domain exceptions, logging full detail server-side and sending a generic `{"type": "error", "code": "internal_error", ...}` frame — the same "any other failure must still be visible to the client, not a silent hang" reasoning as `app.core.errors.unhandled_exception_handler`. The frontend's `streamChat()` has a matching fallback: if the connection closes without ever seeing a `done` or `error` frame (this generic handler failing to run, a dropped connection, or any other edge case), it calls `onError` with a generic message rather than leaving the caller's "waiting" state stuck forever.

**Known limitation, accepted rather than fixed:** `_iter_in_thread()`'s background thread has no cancellation signal. If the client disconnects (or the async generator is otherwise abandoned) before the underlying `generate_content_stream()` iterator is exhausted, the worker thread keeps calling it — continuing to consume the real Vertex AI stream and pushing items onto a queue nothing drains — until the SDK's own iterator ends on its own. This is a real resource/cost concern in a production system handling many concurrent disconnects, but is accepted here given this project's demo scale (a handful of manual/interview-conversation requests, not concurrent production traffic) rather than adding `threading.Event`-based cancellation plumbing to close the gap. Revisit if this project's scale assumptions change.

**Frontend transport: manual SSE-over-`fetch`, not `EventSource`.** The browser's native `EventSource` API cannot send a POST body, and `/chat` needs one (`restaurant_id`, `question`). The frontend instead uses `fetch()` with a `ReadableStream` reader, parsing `data: ...\n\n` frames itself — the format is simple enough that a dependency isn't justified for one endpoint.

## Consequences

- `/chat`'s response contract is a **breaking change** from Phases 3–5: it used to return one `{data, error}` JSON envelope; it now returns an SSE stream. Anyone testing it with a plain `curl -d ...` will see raw SSE frames, not the old single JSON body — called out explicitly in `CLAUDE.md` so this doesn't read as a regression to a future reader.
- `/campaigns` deliberately stays non-streaming (a single JSON response, unchanged) — campaign copy is short, and the "watch it appear" value streaming provides for a longer conversational answer doesn't apply the same way to a short marketing message. This is a considered non-goal, not an oversight.
- The thread-per-stream bridging pattern (`_iter_in_thread`) is contained entirely inside `llm_client.py` — nothing above the SDK-adapter boundary needs to know a thread is involved at all, consistent with the existing "only `llm_client.py`/`embedding_client.py` touch SDK/transport-level concerns" convention.
- Real Vertex AI streaming chunk granularity/latency can't be verified without live credentials — same gap as every prior phase's SDK-touching work. Fixture-built `GenerateContentResponse` chunks prove the plumbing; UAT-6.1/6.4 are flagged as needing live credentials to confirm the real experience.

## Alternatives Considered

- **WebSockets.** Rejected: this endpoint's interaction shape (one request, one response stream, connection closes) doesn't need bidirectional messaging, and WebSockets would add connection-lifecycle complexity (reconnect handling, message framing beyond what SSE already gives for free) with no corresponding benefit here.
- **Client-side simulated streaming (typewriter effect over the original single-JSON `/chat`).** This was the explicit alternative posed to and rejected by the user before this plan was written — see Context above. Simpler, but deviates from "streamed responses... rendered as they arrive" in a way that would misrepresent the architecture in an interview conversation about it.
- **Buffering the full answer server-side and only then "fake-streaming" it back to the client in chunks.** Rejected for the same reason as the client-side option — it isn't actually streaming the model's real token generation, just re-chunking an already-complete response, and would make the "log full response after stream completes" mitigation trivial/meaningless (there's nothing to lose by buffering if you already have the whole thing).
