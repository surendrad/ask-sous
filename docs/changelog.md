# Ask Sous — Changelog

## Phase 0: Project Foundation (2026-07-15)

Stood up every piece of infrastructure Ask Sous needs before any feature work begins:

- **Repository & tooling:** monorepo layout (`backend/`, `frontend/`), Ruff configured for the backend, Biome configured for the frontend, `.pre-commit-config.yaml` (not yet installed — no `.git` directory this session).
- **Environment & secrets:** `.env.example` (root + frontend), `.gitignore`, and `docs/reference/gcp-setup.md` — the one-time manual GCP/Vertex AI checklist.
- **Database:** `docker-compose.yml` (Postgres + pgvector, backend), Alembic (async template) initialised, migration `0001` enables the `vector` extension, migration `0002` creates the dedicated read-only role (`ask_sous_readonly`) — proven by integration test to be unable to write, insert, or create objects. See `docs/decisions/002-readonly-postgres-role.md`.
- **Backend shell:** FastAPI app with `GET /health`, the `{data, error}` response envelope, structured JSON logging via `structlog`, and a global exception handler that never leaks internal error details to clients.
- **Frontend shell:** Vite + React + TypeScript + Tailwind v4 + shadcn/ui, with the full Warm Ember design system (colours, typography, spacing, radii, shadows) wired in as CSS custom properties under `[data-theme]`, dark-first with full light-mode support. A single `HealthCheckPage` proves the shell can reach the backend.

**Deviations from the phase plan, discovered during implementation:**

- **Read-only role password binding:** the plan's assumption that `CREATE ROLE ... PASSWORD :pwd` would work as a driver-level bind parameter was wrong — Postgres's grammar for that clause only accepts a string literal, not a parameter placeholder. Fixed using `sa.bindparam(..., literal_execute=True)`, which renders the value as a properly escaped literal at compile time. Documented in ADR-002.
- **CORS:** the plan didn't account for the Vite dev server (port 5173) and FastAPI (port 8000) being different origins. Added `CORSMiddleware` to `main.py`, scoped to `http://localhost:5173`.
- **Docker unavailable in the implementation environment:** Docker is not installed, so `docker-compose up` and the Docker-based end-to-end health check could not be executed or verified directly. Substituted a local Postgres 17 + pgvector installation (via Homebrew) to actually run and verify every migration and integration test, and ran the FastAPI app as a standalone `uvicorn` process (verified live via `curl`) instead of inside a container. `docker-compose.yml` and `backend/Dockerfile` are still written exactly per the plan and are the documented, shipped way to run this project — they just weren't executable in this session. UAT-0.1 (which requires `docker-compose up`) is left for the user to run once Docker is available locally.

**Tests:** 12 backend tests (config fail-fast, `/health` envelope shape, error handlers, DB bootstrap/readonly-role boundary — 3 tests), 2 frontend tests (`HealthCheckPage` loading/success/error states). All passing. `ruff check`/`format` and `biome check` both clean. `pip-audit` and `npm audit`: 0 vulnerabilities.

**Code review + simplify pass:** an independent code-reviewer agent found no must-fix issues (the readonly-role migration's `literal_execute=True` password handling and the frontend's shadcn-token remapping in `index.css` both checked out correct against spec) and two small should-fix items (`biome.json` was silently excluding `frontend/tests/` from lint/format; `.gitignore` was missing `*.egg-info/`) — both fixed. A follow-up four-angle simplify pass (reuse/simplification/efficiency/altitude) found and fixed: the repo-root `.env`-locating logic, previously hand-duplicated three ways with fragile `parents[N]` path arithmetic, consolidated into `app/core/paths.py::REPO_ROOT`; the read-only role name, previously a literal typed in both the migration and the test fixture, consolidated into `app/core/config.py::READONLY_DB_ROLE`; `backend/Dockerfile`'s layer order, which forced a full dependency reinstall on every code change, fixed to only reinstall when `pyproject.toml` changes; `StatusTag.tsx` switched to the project's own `cn()` class-merging utility instead of a raw template literal; and `test_db_bootstrap.py`'s duplicated probe-table setup/teardown consolidated into a `probe_table` fixture. One efficiency suggestion (module-scoped DB test fixtures) was tried and reverted — it broke tests, since `asyncpg` connections are bound to the event loop they were created in and pytest-asyncio uses a per-test event loop by default; function-scoped fixtures are correct here despite the extra connection overhead.

## Phase 1: Data Layer (2026-07-15)

Full schema and a deterministic, deliberately-patterned seed script:

- **Schema:** six SQLAlchemy models (`restaurants`, `menu_items`, `transactions`, `transaction_items`, `reviews`, `campaigns`) in `backend/app/db/models.py`, one Alembic migration (`create_core_schema`). UUID primary keys, `created_at`/`updated_at` on every table, CHECK constraints on every closed-set string column instead of native Postgres ENUMs, nullable `vector(768)` columns on `reviews.embedding`/`campaigns.embedding` (populated in Phase 4 — see ADR-003). A composite `(restaurant_id, transaction_time)` index on `transactions` for the access pattern every Phase 2 aggregation tool will use. Proven, not assumed: the `ask_sous_readonly` role automatically gained `SELECT` on all six new tables via Phase 0's `ALTER DEFAULT PRIVILEGES` mechanism, verified by a parametrized integration test across every table.
- **Seed script:** `backend/app/seed/generators.py` (pure, DB-free statistical generators, explicit `rng`/`faker` dependency injection — no global seeding) and `backend/app/seed/seed.py` (thin orchestration, bulk Core-level inserts). Five hardcoded restaurant profiles, a fixed 90-day calendar window ending 2026-07-14, deterministic UUIDs drawn from the seeded RNG. Three deliberate, hand-verifiable patterns baked in — Golden Skillet's Tuesday slowdown, Bella Notte's Truffle Fries trend, and Sakura Table's premium ticket size (an addition beyond the two examples `implementation-plan.md` names, added specifically to give Phase 2's cohort-comparison tool something real to detect) — plus two control restaurants with no pattern at all, so the deviations are provably deliberate. Full writeup, exact constants, and verification queries in `docs/reference/seed-patterns.md`. See ADR-004.
- **Actual seeded volume:** 5 restaurants, 59 menu items, 36,877 transactions, 93,866 transaction items, 138 reviews, 16 campaigns.

**Deviation from the phase plan, discovered during implementation:** `alembic revision --autogenerate` initially produced an empty migration — `app/db/migrations/env.py` set `target_metadata = Base.metadata` but never imported `app.db.models`, so no tables had registered themselves on that metadata by generation time. Fixed by adding `from app.db import models  # noqa: F401` to `env.py`. Also hand-corrected the autogenerated migration's missing `pgvector.sqlalchemy` import and reformatted it to match the project's Ruff style, per the plan's documented "review before applying" step for autogenerate output.

**Tests:** 32 new tests (10 schema/migration, 11 seed-generator unit tests, 9 seed-integration tests, 2 pipeline/readonly-role tests) — full suite now 44 tests (12 from Phase 0 + 32 new), all passing. Every deliberate pattern is tested twice: once against the generator's in-memory output (DB-free, fast) and once via direct SQL against the real seeded database (proving the pattern survives the DB round-trip). `ruff check`/`format` clean.

**Code review:** an independent code-reviewer agent found two must-fix issues, both corrected:

1. **`Mapped[float]` instead of `Mapped[Decimal]`** on five numeric columns (`MenuItem.price`, `Transaction.total_amount`, `TransactionItem.unit_price`, `Campaign.conversion_rate`/`revenue_lift`) — contradicted the phase plan's own spec, and SQLAlchemy's `Numeric` type actually returns `Decimal` at runtime regardless of the annotation, so Phase 2's ORM-based aggregation code would have hit a type mismatch the moment it touched these fields. Fixed.
2. **The Bella Notte "last 30 days" SQL bucket was actually 60 days** (an `ELSE` branch covering the whole back half of the 90-day window, not a symmetric last-30 window) — the reported "~5.2x" trend overstated the real effect; the correctly-bucketed query gives **~3.0x**, matching the pattern's own designed prediction exactly. Fixed in both `test_seed_integration.py` and `docs/reference/seed-patterns.md` (numbers regenerated from the corrected query). This mattered more than a typical off-by-one, since this document is the one every later phase is told to trust as verifiable ground truth.

Also addressed: deduplicated inline UUID-generation logic in `seed.py` (now calls `generators.rng_uuid()` instead of re-implementing it), and closed a test-coverage gap — added `test_check_constraints.py` (7 tests), proving every CHECK constraint the schema defines (`ck_restaurants_size_category`, `ck_transactions_payment_type`/`channel`, `ck_transaction_items_quantity`, `ck_reviews_rating`/`source`, `ck_campaigns_channel`) actually rejects an invalid value, not just the FK-violation case the original smoke test covered. Full suite now 51 tests, all passing; re-seeding after these fixes produced byte-identical row counts to the pre-fix run, confirming determinism held throughout.

## Phase 2: Aggregation Tools (2026-07-15)

The four pre-built aggregation tools named in master-plan.md §4.2, built as plain testable async Python functions — this is the first phase where the `ask_sous_readonly` role (ADR-002) is used for real feature work, not just tested in isolation:

- **Read-only connection path:** `backend/app/agent/tools/db.py` — `readonly_database_url()` + `readonly_connection()`, the only place `app/agent/` code is permitted to open a database connection. A fresh engine per call, not a cached singleton (see ADR-005 — this is a deliberate trade-off against the exact event-loop-binding bug Phase 0 already hit once and reverted a fix for). `Settings` gained a typed, fail-fast `readonly_db_password` field so application code no longer reaches into `os.environ` directly the way the migration and test fixtures did.
- **`get_revenue_summary()`** (`revenue_summary.py`) — total revenue, transaction count, average ticket, and a daily breakdown for a restaurant/date-range, the building block every other tool in this phase either calls or mirrors.
- **`get_item_velocity()`** (`item_velocity.py`) — splits a window into even halves and reports each menu item's quantity change and trend (`up`/`down`/`flat`), with a hardcoded ±15-percentage-point threshold before calling it a real trend rather than noise.
- **`compare_periods()`** (`period_comparison.py`) — day-over-day and week-over-week comparison as the same mechanism at different granularities (a period's length determines the prior period's length); reuses `get_revenue_summary()` rather than duplicating its SQL.
- **`get_cohort_comparison()`** (`cohort_comparison.py`) — one restaurant's metric (average ticket / total revenue / transaction count) against the pooled peer average, selected via a small hardcoded allow-list dict (`_METRIC_EXPRESSIONS`) with a runtime `ValueError` guard — the one place in this phase that selects a SQL fragment by argument value, called out explicitly per CLAUDE.md's "no dynamic identifiers from LLM output" rule, since `metric` is exactly the kind of value Phase 3's function-calling will eventually hand this function as a plain string.

Every tool follows the pure/impure split Phase 1's `generators.py`/`seed.py` established: a pure computation function (`_summarize_daily_rows`, `_build_item_velocities`, `_prior_period`/`_compare`, `_ratio`) unit-tested with fixture data, no database, no event loop — plus a thin async wrapper.

**Correctness, verified against `docs/reference/seed-patterns.md`'s exact documented numbers, live:**
- Golden Skillet's Tuesday average via `get_revenue_summary()`: **$1,354.19** (documented: $1,354.40) — a 57.7%-class gap, comfortably clearing the tests' 40%-margin bar.
- Sakura Table's cohort ratio via `get_cohort_comparison()`: **2.11x** (documented: ~2.1x) — restaurant value $83.33, peer value $39.41, matching the published figures almost exactly.
- Bella Notte's Truffle Fries trend: the tool's own even-halves split gives ~2.1x (723 → 1,518 units) — a different, non-contradictory number from `seed-patterns.md`'s first/last-30-with-middle-excluded ~3.0x methodology, since they measure the same underlying pattern at different granularities. Both are tested explicitly; a direct thirds-style cross-check (two separate `get_item_velocity()` calls reproducing the document's exact bucketing) confirms the ~3.0x figure too.

**Tests:** 49 new tests (unit tests for every pure function across all four tools, integration tests against the real seeded database for each tool's empty-range and populated-range behavior, 4 read-only-boundary spy tests proving each tool genuinely goes through `readonly_connection()`, 9 pattern-verification tests, 2 cross-tool consistency checks) — full suite now 100 tests (51 from Phase 0/1 + 49 new), all passing. `ruff check`/`format` clean.

**Deviations from the phase plan, discovered during implementation:**
- **asyncpg can't infer a bind parameter's type when its value is `None`.** `get_item_velocity()`'s optional `menu_item_name` filter (`m.name = :menu_item_name`) failed with `AmbiguousParameterError` when called without a filter. Fixed with an explicit `CAST(:menu_item_name AS text)` — note that SQLAlchemy's `text()` parser doesn't handle the more idiomatic `:menu_item_name::text` double-colon cast syntax correctly (it left the literal, unsubstituted parameter markers in the compiled SQL), so `CAST(... AS ...)` is the pattern to use for any future optional-filter bind parameter in this codebase.
- **Test file naming collision:** `tests/unit/test_agent_tools_db.py` and a same-named file under `tests/integration/` collided at pytest's module-import level (no `__init__.py` in either test directory). Renamed the integration file to `test_agent_tools_db_integration.py`, matching this project's established `_integration.py` suffix convention for files that share a base name with a unit-test counterpart.
- **`tests/integration/conftest.py`'s `readonly_engine` fixture** was refactored to call the new `app.agent.tools.db.readonly_database_url()` instead of its own hand-rolled copy of the same URL-building logic, now that production code provides it — one less place that logic could silently drift.

## Phase 3: Agent Core — Insights Q&A (2026-07-16)

The agent orchestration layer: Vertex AI function-calling over the four Phase 2 aggregation tools plus a new raw SQL tool, grounding/audit logging, and a `/chat` API endpoint. Two new runtime dependencies: `google-genai` (official Vertex AI SDK) and `sqlglot` (structural SQL validation for the raw SQL tool).

- **`GeminiClient`** (`backend/app/agent/llm_client.py`) — the only module anywhere in `app/agent/`/`app/api/` permitted to import `google.genai`. Accepts and returns only this app's own frozen dataclasses (`ToolDeclaration`, `UserText`/`ModelToolCalls`/`ToolResultsTurn`, `ToolCallRequest`/`FinalAnswer`) — never a raw SDK type — so every layer above it is testable with plain `AsyncMock` and zero GCP dependency. See ADR-007.
- **`tool_registry.py`** — hand-written `ToolDeclaration` (plain JSON-schema dicts) for all five tools, a `TOOL_DISPATCH` table pairing each with `parse_args()` (model JSON → real typed kwargs) and the actual tool function, and `_to_jsonable()`, the single serializer used both for the result fed back to the model and the result logged for the audit trail (Decimal → exact string, never a float; UUID/date → ISO string).
- **`run_readonly_query()`** (`backend/app/agent/tools/raw_sql.py`) — the new raw SQL tool, letting the model answer questions the pre-built tools can't. Three independent defence layers: `sqlglot`-based structural SELECT-only validation (rejects writes anywhere in the tree, including inside a CTE), a hard row cap via query wrapping, and a statement timeout — all on top of the existing `ask_sous_readonly` DB role. See ADR-006.
- **`answer_question()`** (`backend/app/agent/insights.py`) — the orchestration loop: drives the model through function-calling rounds (`MAX_TOOL_CALL_ROUNDS = 5`) until a final answer, catching and feeding back tool errors rather than crashing, and raising `AgentIncompleteError` if the round cap is exceeded. Every turn logs `agent_turn_started`/`tool_call_requested`/`tool_call_result`/`agent_turn_model_selected`/`agent_turn_completed` via structlog, all correlated by a per-turn `turn_id` bound with `structlog.contextvars` and cleared in a `finally` block (verified to clear even when the loop raises). A best-effort `_check_grounding()` warns (never blocks) when an answer contains digits but no tool was called that turn — CLAUDE.md's "no naked numbers" rule, backed by a guard test proving the test suite itself would catch a genuinely ungrounded response.
- **`POST /chat`** (`backend/app/api/chat.py`) — the access point, chosen over a throwaway CLI script since Phase 6 needs this endpoint regardless and all the FastAPI/envelope/exception-handler scaffolding already existed. Checks restaurant existence via the same `readonly_connection()` path every tool uses (404 `restaurant_not_found` if missing), calls `answer_question()`, and returns the full `tool_calls` array in the response body (not just server-side logs) so a demo can show "here's what it actually queried" directly from the API response. Two new exception handlers: `AgentUnavailableError` → 503 `agent_unavailable`, `AgentIncompleteError` → 502 `agent_incomplete` — both generic-message-only, full detail logged server-side, zero automatic retries.

**Mid-phase correction:** the initial implementation of `tool_registry.py` and `insights.py` imported `google.genai.types` directly to build `Tool`/`Content`/`Part` objects, silently defeating the "mock at the adapter boundary" testing strategy the plan called for (those modules' own tests would have needed SDK-shaped fixtures, and any SDK type change would break them directly). Caught by the phase's own explicit refactor checklist item (`grep -rn "from google" app/agent/ app/api/` should show only `llm_client.py`) before it was built on further — reworked to pass plain dataclasses (`ToolDeclaration`, `ConversationEntry` variants) through the adapter boundary instead, with `GeminiClient` doing all `types.*` construction internally.

**Verified against real fixtures, not live Vertex AI:** everything in this phase — including a full end-to-end test driving `POST /chat` through a real Phase 2 tool against the real seeded database, real structured logging, and the real response envelope, with only `GeminiClient` mocked — is tested and verified without live GCP credentials, since none exist in this environment (`.env` still has placeholder values; `docs/reference/gcp-setup.md`'s checklist hasn't been run). UAT-3.1 through UAT-3.4 are completable now (mocked-model scenarios); UAT-3.5 and UAT-3.6 explicitly require live credentials and are not yet verified. A manual pass confirmed the full `/chat` JSON response and a complete turn's structlog output (all events sharing one `turn_id`) are both correct and human-reconstructable end-to-end.

**Code review:** an independent code-reviewer agent found one must-fix issue, corrected:

1. **The model was never told its `restaurant_id`.** `answer_question()`'s initial conversation history was seeded with only the user's question — `restaurant_id` appeared nowhere in what would be sent to a real Gemini call, so against a live API the model would have had to guess or invent a `restaurant_id` argument for every one of the four restaurant-scoped tools, a direct break of the "ask about your own data" flow and a violation of the grounding intent this phase exists to enforce. Invisible in the original test suite because every test mocked `generate_turn` and hand-supplied a correct `restaurant_id` in the fixture. Fixed: `INSIGHTS_SYSTEM_INSTRUCTION` became `build_insights_system_instruction(restaurant_id)`, templating the restaurant's UUID directly into the system instruction passed to every `generate_turn()` call; a new test (`test_insights_system_instruction.py`) asserts the constructed instruction actually contains it.

Also addressed two should/consider-level findings: `tool_call_requested` now logs the parsed, real-typed tool arguments (post-`parse_args()`) rather than the raw, unparsed model JSON, matching the phase plan's documented logging convention (new test: `test_tool_call_requested_logs_parsed_args_not_raw_model_json`); and `raw_sql.py`'s `_WRITE_NODE_TYPES` now includes `exp.Command` alongside the other seven rejected node types, matching the plan's full list exactly (defense-in-depth completeness — the DB-level read-only role was already the documented backstop for this gap either way).

**Tests:** 63 new tests (4 `GeminiClient` adapter/translation tests, 18 `tool_registry` schema/serialization/parse-args tests, 12 raw-SQL validation + integration tests, 4 orchestration-loop tests, 8 logging/grounding tests, 6 grounding-guard tests proving the guard itself works, 5 `/chat` endpoint tests, 2 SDK-error-translation tests, 2 cross-cutting end-to-end/malformed-input integration tests, 1 system-instruction test, 1 code-review-fix logging test) — full suite now 161 tests (100 from Phase 0–2 + 61 new + 2 code-review fixes), all passing. `ruff check`/`format` clean.

**`/simplify` pass** (four parallel review angles — reuse, simplification, efficiency, altitude), applied after code review:
- **Deleted the hand-rolled JSON-schema → `types.Schema` converter** (`_schema_dict_to_schema`/25 lines) in `llm_client.py` — the reuse review caught that `types.FunctionDeclaration.parameters_json_schema` already accepts a plain JSON-schema dict directly, verified against the installed SDK before applying (`FunctionDeclaration(parameters_json_schema=...)` constructs correctly). `ToolDeclaration.parameters` now passes straight through.
- **Concurrent tool-call execution** — `answer_question()`'s tool-call round now runs independent tool calls via `asyncio.gather()` instead of a sequential `for` loop; each call hits its own DB query with no dependency between them, so a multi-tool round now takes roughly as long as its slowest call instead of their sum.
- **Generic exception-handler factory** (`_make_domain_exception_handler()` in `app/core/errors.py`) replaced the two near-identical `agent_unavailable_exception_handler`/`agent_incomplete_exception_handler` functions — both the simplification and altitude reviews converged on this independently. Adding the next domain exception is now one factory call, not a new copy-pasted function.
- **Shared `_parse_restaurant_and_date_range()` helper** in `tool_registry.py` replaced three structurally-identical `_parse_*_args` functions (revenue summary, compare periods, cohort comparison all parse a UUID + two ISO dates, differing only in field names).
- **Skipped, with reasons:** reusing a single `GeminiClient` across requests instead of constructing one per `answer_question()` call (real but out of proportion for a demo-scale project, and would require reworking the test-patching pattern every orchestration test currently relies on); extracting a shared restaurant-existence-check helper used by both `chat.py` and Phase 2's `cohort_comparison.py` (would mean editing already-shipped, already-tested Phase 2 code — outside this phase's diff); setting `statement_timeout` once at the connection level instead of per raw-SQL call (marginal gain, adds complexity to the deliberately-per-call-engine pattern ADR-005 already established).

Full suite re-verified at 161 tests passing, `ruff check`/`format` clean, after all `/simplify` fixes.

## Phase 4: Vector Retrieval (2026-07-16)

Qualitative grounding: embeddings for reviews/campaigns and a pgvector similarity search tool, extending Phase 3's agent toolset to six tools. No new runtime dependencies — `pgvector` and `google-genai` were already added in Phases 0/3.

- **`EmbeddingClient`** (`backend/app/agent/embedding_client.py`) — a second, narrowly-scoped Vertex AI adapter alongside `GeminiClient`, mirroring its pattern exactly: `embed_texts(list[str]) -> list[list[float]]`, no raw SDK type ever crosses the boundary. `_validate_dimensions()` catches a model/config mismatch immediately (naming the offending index) rather than letting a malformed vector fail obscurely at the DB insert. See ADR-008.
- **`embed_seed_data.py`** (`backend/app/seed/embed_seed_data.py`) — a follow-up script to `seed.py` (kept separate so plain seeding still needs zero GCP dependency), populating `reviews`/`campaigns.embedding` in batches of 100 via the privileged session path (never `readonly_connection()` — this writes). Idempotent by construction (verified by a dedicated test): re-running produces byte-identical embeddings.
- **`vector_search.py`** (`backend/app/agent/tools/vector_search.py`) — `search_reviews()` (registered as the sixth LLM-callable tool, `search_customer_reviews`) and `search_similar_campaigns()` (built now, deliberately left unregistered for Phase 5 to call directly). Cosine distance (`<=>`), a vector literal bound as an ordinary text parameter and `CAST` to `vector` in SQL rather than asyncpg-level codec registration, no ANN index at this data scale (~150 total vectors). See ADR-009.
- **System instruction updated** (`insights_system_instruction.py`) with explicit qualitative-grounding guidance: use `search_customer_reviews` for sentiment/opinion questions, never invent review content, say so honestly when a search returns no matches.

**A real gap found and fixed during manual verification, not code review this time:** running `embed_seed_data.py` against this environment's placeholder `.env` produced a raw, unhandled `google.auth.exceptions.DefaultCredentialsError` stack trace instead of failing through the domain exception path — neither `EmbeddingClient` nor (it turned out) `GeminiClient` caught auth/credential failures, only SDK-level API errors. Fixed in both adapters by also catching `google.auth.exceptions.GoogleAuthError`. This was a latent gap in `GeminiClient` since Phase 3 that simply hadn't been exercised by an actual script run against placeholder credentials until this phase's manual verification step did so.

**Verified against real fixtures and hand-crafted vectors, not live Vertex AI:** the actual pgvector `<=>`/`ORDER BY`/`LIMIT`/restaurant-scoping SQL is proven correct by inserting hand-crafted vectors directly into real seeded rows and querying against the real Postgres+pgvector instance — this verifies the query logic without needing semantically real embeddings or live credentials. A full end-to-end test drives `POST /chat` through `search_customer_reviews` → real pgvector query → real logging → real envelope, with only `GeminiClient`/`EmbeddingClient` mocked. UAT-4.1 through UAT-4.3 are completable now; UAT-4.4 (population script against real data) and UAT-4.5 (semantic relevance of real search results) explicitly require live credentials and are not yet verified.

**Tests:** 34 new tests (5 `EmbeddingClient` adapter/translation tests including auth-error translation, 6 `embed_seed_data` unit + 4 integration tests, 9 `vector_search` unit tests, 3 hand-crafted-vector integration tests proving real pgvector ordering/scoping/empty-state behaviour, 2 sixth-tool registration/parse-args tests, 1 system-instruction test, 1 cross-cutting `/chat` end-to-end test with the new tool, 2 credential-failure-translation tests split across both adapters) — full suite now 195 tests (161 from Phase 0–3 + 34 new), all passing. `ruff check`/`format` clean.

## Phase 5: Campaign Generation (2026-07-16)

A second agent capability alongside insights Q&A, plus real model routing: Flash/Pro escalation for insights, always-Pro for campaign copy. No new runtime dependencies.

- **Model routing** (`_select_model()` in `backend/app/agent/insights.py`) — evaluated at the top of every round in `answer_question()`'s loop, not once per turn, so a turn can start on `FLASH_MODEL` and escalate to the new `PRO_MODEL` (added to `llm_client.py`) mid-turn once it's genuinely needed `ESCALATION_TOOL_CALL_THRESHOLD` (3) rounds without reaching a final answer. An explicit "deeper analysis" keyword match (`"deep dive"`, `"thorough"`, etc.) escalates immediately, taking priority over the round count. `agent_turn_model_selected` now logs a `routing_reason` (`"default"` / `"tool_call_threshold"` / `"keyword"`) alongside the model. See ADR-010.
- **`campaigns.py`** (`backend/app/agent/campaigns.py`) — `generate_campaign()`, deliberately **not** a multi-round tool-calling loop like `answer_question()`: a single retrieve-then-generate turn. Fetches the restaurant's `brand_voice_guide` (`restaurant_lookup.py`, new — a small module for restaurant-scoped lookups that don't fit the aggregation-tool or raw-SQL-tool shape), retrieves up to 2 similar past campaigns via Phase 4's already-built-but-unregistered `search_similar_campaigns()`, builds a system instruction (`campaign_system_instruction.py`, new), then one `GeminiClient.generate_turn()` call with `tools=[]`, always on `PRO_MODEL`. Proceeds normally (not an error) when zero past campaigns exist — generates from brand voice alone and notes their absence in the prompt. Same per-turn `turn_id`-correlated audit logging pattern as `answer_question()`: `campaign_turn_started` / `campaign_examples_retrieved` / `campaign_turn_completed`.
- **`POST /campaigns`** (`backend/app/api/campaigns.py`) — mirrors `/chat`'s shape closely: `{restaurant_id, brief}` in, `{copy_text, examples_used, model}` out inside the standard envelope, same 404/422/503/502 error handling (reuses `AgentUnavailableError`/`AgentIncompleteError` and their existing handlers unchanged — no new exception class needed). Registered in `main.py`.
- **Reuse fix during implementation:** `/chat`'s restaurant-existence check was a private helper duplicated verbatim into the new `/campaigns` endpoint at first draft; extracted into a shared `restaurant_exists()` in `restaurant_lookup.py` instead, used by both endpoints.
- Generated campaign copy is returned to the caller only — this phase does not persist it back to the `campaigns` table (no "save/send" feature is in scope per master-plan.md).

**Verified against fixture/mocked Vertex AI responses and hand-crafted embeddings, not live Vertex AI** — same caveat as Phases 3 and 4. A full end-to-end test drives `POST /campaigns` through real brand-voice lookup → real pgvector query against a hand-embedded campaign row → real logging → real envelope, with only `GeminiClient`/`EmbeddingClient` mocked. - **Efficiency:** `generate_campaign()`'s brand-voice lookup and past-campaign retrieval were two independent I/O calls (a DB round-trip, and an embedding call + separate DB round-trip) run sequentially with no data dependency between them. ## Phase 6: Frontend (2026-07-16)

The demoable product: a real UI over everything built in Phases 1–5, plus genuine backend streaming — confirmed with the user as a deliberate, documented scope decision before this phase began (implementation-plan.md 6.1 and `stack.md` both call for real token-by-token streaming, not a client-side typewriter simulation over a single JSON response).

**Backend — real SSE streaming for `/chat`, a breaking contract change:**
- `GeminiClient.generate_turn_stream()` (`llm_client.py`) — bridges `google-genai`'s synchronous `generate_content_stream()` iterator onto the event loop via a new `_iter_in_thread()` helper (background thread + `asyncio.Queue`), yielding `TextChunk` events as a final-answer round's text arrives and a terminal `ModelToolCalls`/`FinalAnswer` event, mirroring `generate_turn()`'s translation logic.
- `answer_question_stream()` (`insights.py`) — same model-routing/tool-dispatch/grounding/audit-logging behavior as `answer_question()` (kept, unchanged, as the simplest non-streaming entry point for any future non-UI caller), sharing a newly-extracted `_resolve_tool_call_round()` helper to avoid duplicating the per-round tool-dispatch-and-logging block across both.
- `POST /chat` is now a Server-Sent-Events endpoint (`text/event-stream`), not the standard `{data, error}` envelope — `text_chunk`/`done`/`error` frames. A failure before the first event is produced still returns a normal 503/502 JSON response through the existing exception handlers; a failure after streaming has started becomes a final `error` SSE frame instead — an inherent SSE constraint (the HTTP status is already committed), not a design choice. Full rationale in ADR-011.
- `GET /restaurants` (new) backs the frontend's restaurant switcher; `restaurant_exists()`/`list_restaurants()` added to the shared `restaurant_lookup.py`.
- CORS origins widened from a single hardcoded `localhost:5173` to a small range (`5173`–`5175`), since Vite auto-increments past an already-taken port — discovered during manual verification when an unrelated project's dev server was already holding 5173 on the same machine.

**Frontend — full React app** (`frontend/src/`): `lib/api.ts` (`streamChat()` — manual SSE-over-`fetch` parsing, since the browser's `EventSource` can't send a POST body; `getRestaurants()`; `generateCampaign()`), `lib/restaurant-context.tsx` (shared selected-restaurant state), `components/{ChatMessage,CitationChip,ThinkingIndicator,RestaurantSwitcher,AppShell}.tsx`, `pages/{ChatPage,CampaignsPanel}.tsx`, and `App.tsx` rewired as the real root (loads restaurants via TanStack Query, replacing Phase 0's `HealthCheckPage` as the default view — kept in the codebase as a manual backend-reachability check, just no longer mounted by default). `RestaurantSwitcher` deliberately uses a styled native `<select>` instead of a headless dropdown-menu primitive — fully accessible out of the box and far more reliable to test than a portal-based popup, for a component that's purely a data-context switch.

**Code review + manual verification found and fixed two real issues, not just theoretical ones:**
- **Should-fix (code review):** the SSE endpoint's mid-stream error handling only caught the two domain exceptions (`AgentUnavailableError`/`AgentIncompleteError`) — any other unexpected exception mid-stream would silently close the connection with no error event, leaving the frontend's "thinking"/streaming state stuck forever. Fixed on both ends: the backend now catches a bare `Exception` mid-stream too (logging full detail, sending a generic `internal_error` frame, mirroring `unhandled_exception_handler`'s shape), and `streamChat()` now calls `onError` if a stream ever closes without seeing a `done` or `error` frame at all, as a second line of defense.
- **Real bug (manual browser verification, not code review):** switching restaurants didn't reset `ChatPage`/`CampaignsPanel`'s own state — the previous restaurant's chat history and campaign draft stayed visible after switching, since only the `restaurantId` prop changed on an already-mounted component instance. Fixed by mounting both with `key={selectedRestaurant.id}` in `App.tsx`, forcing a remount on switch; locked in with a regression test.
- **Documented, not fixed:** `_iter_in_thread()`'s background thread has no cancellation signal — if a client disconnects mid-stream, the worker thread keeps consuming the real Vertex AI stream until the SDK's iterator ends on its own. Accepted given this project's demo scale rather than adding `threading.Event`-based cancellation plumbing; recorded explicitly in ADR-011 as a known limitation to revisit if that assumption changes.

**Verified against a real running backend + seeded Postgres database, not just mocks** — a genuine departure from every prior phase's fixture-only verification, made possible because this phase's core work (SSE plumbing, UI rendering, restaurant scoping) doesn't require live Vertex AI credentials to exercise meaningfully. Used Playwright MCP to drive a real browser against `localhost:5174` + `localhost:8000`: confirmed the sidebar/split-view layout matches `docs/definition/design-system.html`, the restaurant switcher lists all 5 real seeded restaurants, the thinking indicator and error banner render correctly, and — critically — captured the real backend log trace proving the "before-first-chunk failure → plain 503 JSON, not an SSE error frame" path from ADR-011 actually happens exactly as designed (a genuine `DefaultCredentialsError` from the missing GCP credentials, translated end-to-end through `AgentUnavailableError` to the JSON response the UI correctly displayed).

**Known, explicitly acknowledged gap:** implementation-plan.md's Phase 6 Testing section calls for automated Playwright E2E smoke tests. This phase used a manual Playwright-MCP pass instead (see above) — no Playwright test files/config were committed. A deliberate time-boxed trade-off, not an oversight; tracked as an open item in `docs/uat.md`'s Phase 6 section rather than silently dropped. Same live-credentials caveat as every prior phase for the parts that do need it: UAT-6.1's real streaming feel and UAT-6.4's real mid-stream failure both remain unverified against a live model until `docs/reference/gcp-setup.md` is completed.

**Tests:** 12 new/changed backend tests (3 `_iter_in_thread` unit tests, 3 `generate_turn_stream` unit tests, 4 `answer_question_stream` tests, 2 new SSE-endpoint tests for the generic mid-stream-exception path, plus 3 pre-existing `/chat` integration tests updated to the streaming contract) — backend suite now 231 tests, all passing. 37 new frontend tests (Vitest/RTL) across `api.ts`, `restaurant-context.tsx`, `ChatMessage`/`CitationChip`/`ThinkingIndicator`/`RestaurantSwitcher`/`AppShell`, `ChatPage`, `CampaignsPanel`, and `App.tsx` (including the restaurant-switch state-reset regression test) — frontend suite now 37 tests, all passing. `ruff check`/`format` and `biome check` both clean.

## Phase 7: Polish (post-MVP) (2026-07-16)

Explicit post-MVP polish per the master plan: a live-trickle background generator so a demo doesn't look frozen in time, and a simple dashboard for the visual weight expected of a data product. Neither is core to the agent story — the MVP (Phases 0-6) already fully proves both grounded Q&A and grounded generation.

**Live-trickle generator** (`backend/app/seed/trickle.py`) — `run_trickle_loop()`, started as a background `asyncio.Task` from FastAPI's `lifespan` only when `ENABLE_TRICKLE=true` (default `false`), cancelled cleanly on shutdown. Deliberately uses genuine `uuid.uuid4()`/`random` module randomness, not `generators.py`'s deterministic seeded RNG — CLAUDE.md's own convention (ADR-004) already scoped reproducible seeding to `seed.py`/`generators.py` only, precisely so a non-deterministic generator like this wouldn't accidentally inherit it. No manual on-demand trigger endpoint, per implementation-plan.md 7.1's explicit testability approach — tests drive `run_trickle_loop()` directly with a short interval and an injectable session maker, cancelling the task after a few ticks. Writes go through the same privileged session path `seed.py` already uses — the agent's read-only DB boundary is scoped to `app/agent/` tool code, not the whole app. See ADR-012.

**Dashboard** (`backend/app/api/dashboard.py` + `frontend/src/pages/DashboardPage.tsx`) — `GET /dashboard?restaurant_id=...` reuses Phase 2's `get_revenue_summary()` and `get_item_velocity()` directly (no new aggregation SQL, and not through the agent — this is deterministic app data a human clicks to see, not something the LLM decides to fetch). Frontend renders a KPI stat-card row + two charts. **Reconciled a real conflict between planning docs:** implementation-plan.md 7.2 names Recharts; design-guidelines.md §11 (the later, more specific `/designer` decision, written with this exact feature in mind) says "CSS-drawn bars, no charting library needed." Followed design-guidelines.md — no new npm dependency. `AppShell`'s Dashboard nav item, a disabled Phase-6 placeholder, is now a real third view: unlike Chat/Campaigns (always both present in the DOM, only CSS-toggled for mobile), switching to Dashboard conditionally renders it *instead of* the split, matching design-guidelines.md's "separate full-width view" framing. See ADR-012.

**Manual verification against a real running backend + database (including a live trickle run) found and fixed two real bugs, not just theoretical ones:**
- **KPI values rendered with 20+ digits of Decimal precision** (`average_ticket` inherits unrounded division from Phase 2's `revenue_summary.py`) — fixed with a `formatCurrency()` helper (`Number(value).toFixed(2)`) at the UI boundary, deliberately not by touching the backend's Decimal math (an API contract shouldn't silently lose precision; display formatting belongs at the display layer). Locked in with a regression test using the exact long-decimal value observed live.
- **Revenue-trend bars rendered at zero height, completely invisible** — a classic CSS gotcha: a percentage `height` style only resolves against an ancestor with an explicitly-set height, and the bar's immediate parent had none (it was sized to content, not stretched, because the row container used `items-end`). Fixed by giving each bar's column wrapper `h-full` and moving the bottom-alignment to `justify-end` on the column itself. Since jsdom doesn't perform real CSS layout, the regression test asserts the structural fix (the `h-full` class is present) rather than a rendered pixel height — the bug was only visible in the actual screenshot-diffed manual pass, not something any unit test could have caught on its own.

**Code review found three should-fix issues, all closed before commit:**
- **`run_trickle_loop()` had no per-tick error handling** — a single failed tick (transient DB error, etc.) would silently kill the background task for the rest of the process's life (the default asyncio behavior for an unhandled task exception is just a "Task exception was never retrieved" line on stderr, easy to miss in a demo session). Fixed with a `try/except` per tick that logs via `structlog` and lets the loop continue on the next interval; locked in with a dedicated resilience test (`test_trickle_loop_resilience.py`) proving the loop survives a failing tick.
- **The dashboard integration test's KPI assertion was a wall-clock time bomb** — it asserted `total_revenue > 0` against a live `date.today()` window while the seed data is frozen at a fixed `SEED_END_DATE`; the test would silently start failing once real time moved more than 7 days past that date. Fixed by pinning `date.today()` in the test via monkeypatch, mirroring the pattern `test_revenue_summary_integration.py` already uses.
- **`docs/uat.md`'s Phase 7 entries stayed "Not Started" while other docs described a manual verification pass that substantively covered some of the same ground** — reconciled by adding an explicit note to UAT-7.4 clarifying exactly what the implementation-time manual pass did and didn't check, rather than marking UATs as passed (that sign-off is the user's own `/uat` pass in production, not something to claim during implementation).
- **Consider-tier:** `getDashboard()` now wraps its `restaurant_id` query param in `encodeURIComponent()` for robustness, even though it's always a backend-supplied UUID today.

**Tests:** 10 new backend tests (2 `insert_trickle_transaction`/`run_trickle_loop` integration tests, 1 trickle-loop-resilience unit test, 2 lifespan enabled/disabled unit tests, 2 `/dashboard` endpoint integration tests with a pinned test date) — backend suite now 238 tests, all passing. 7 new frontend tests (`getDashboard()`, `DashboardPage` KPI/empty-state/currency-formatting/bar-structure/error-state coverage, `AppShell`'s enabled Dashboard nav item and full-width view swap) — frontend suite now 44 tests, all passing. `ruff check`/`format` and `biome check` both clean.
